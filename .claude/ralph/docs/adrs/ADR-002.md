# ADR-002: Super Admin Authentication Model Design

## Context

The ERP system requires a super administrator role that can manage tenants across the multi-tenant system. Key questions:
- How should the super admin authenticate? Via the same JWT flow or a separate system?
- How should the super admin's identity be represented in the tenant-isolated data model?
- How should we avoid accidentally granting cross-tenant access to regular users?

## Decision

We adopted a **System Tenant approach**: the super admin is a regular user within a special "system tenant" (`tenant_id = 00000000-0000-0000-0000-000000000000`).

### Key Design Elements

1. **System Tenant**: A well-known tenant record with all-zero UUID serves as the home for super admin users. This tenant is never used for business operations.

2. **SUPER_ADMIN Role**: A system role (`RoleCodeSuperAdmin = "SUPER_ADMIN"`) with fixed UUID (`SuperAdminRoleID = "00000000-0000-0000-0000-000000000100"`) grants `tenant:*` permissions (read, create, update, delete, suspend, manage).

3. **Same Authentication Flow**: Super admins authenticate via the same JWT login endpoint. The JWT contains `tenant_id = SystemTenantID`, which is checked by the `SuperAdminMiddleware`.

4. **Two-Layer Authorization**:
   - **Layer 1**: `SuperAdminMiddleware` checks `claims.TenantID == SystemTenantID`
   - **Layer 2**: Checks for `SuperAdminRoleID` in role list OR any `tenant:*` permission in claims

5. **Fixed UUIDs**: System tenant, super admin role, and default super admin user all use deterministic UUIDs for idempotent migrations.

## Consequences

### Positive
- Reuses existing authentication infrastructure (JWT, login flow, session management)
- No separate auth system to maintain, reducing operational complexity
- Super admin is just a user with special role — fits naturally into the RBAC model
- Deterministic UUIDs enable idempotent migrations and predictable testing
- Two-layer check (tenant + role) provides defense-in-depth

### Negative
- System tenant must be carefully excluded from tenant listing/management UIs
- If JWT secret is compromised, super admin access is also compromised (same as regular users)
- Fixed UUIDs are discoverable if code is leaked (mitigated by still requiring valid credentials)
- Super admin user shares the same `users` table — needs careful handling in cross-tenant queries

### Alternatives Considered
- **Option A: Separate Authentication System** — Dedicated auth for admins (separate login page, separate JWT issuer). Rejected: doubles auth infrastructure complexity for marginal security benefit.
- **Option B: Special User Flag** — Add `is_super_admin bool` column to users table. Rejected: bypasses RBAC model, creates a parallel authorization path that's harder to audit.
- **Option C: API Key-based Admin Access** — Static API keys for admin operations. Rejected: no session management, no audit trail of who performed actions, key rotation is painful.
- **Option D: External Identity Provider (e.g., Keycloak realm)** — Dedicated admin realm. Rejected: adds external dependency for a feature needed by very few users, over-engineered for the project scale.

## Trade-Offs
- **Pros**: Simple, consistent, auditable, fits DDD/RBAC model
- **Cons**: Shared auth surface, must protect system tenant carefully
- **Risk Level**: 🟢 LOW — Standard pattern for SaaS admin access; system tenant isolation is enforced at middleware level

Accepted
