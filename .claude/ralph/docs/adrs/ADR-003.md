# ADR-003: Cross-Tenant Query and Audit Log Design

## Context

The super admin needs to:
1. Query data across all tenants (tenant list, stats, user counts)
2. Modify tenant state (suspend, activate, change plan, update quotas)
3. Have all actions audited for compliance and accountability

The system uses row-level tenant isolation (`tenant_id` on every table) with GORM scopes that automatically filter by tenant. Cross-tenant operations must bypass this isolation safely.

## Decision

### Cross-Tenant Query Design

1. **Dedicated Admin Repository Layer**: Admin operations use separate repository methods that explicitly skip the automatic `tenant_id` filter. These methods are only accessible through the `AdminTenantService` application service.

2. **No Global Scope Bypass**: We do NOT disable the tenant filter globally. Instead, admin queries explicitly use `Unscoped()` or query the `tenants` table directly (which has no tenant_id filter since it IS the tenant table).

3. **Admin API Namespace**: All cross-tenant endpoints are under `/api/v1/admin/*`, protected by `SuperAdminMiddleware`. Regular tenant-scoped APIs remain unchanged.

4. **Read-Only Cross-Tenant Access**: The super admin can read aggregate statistics across tenants but cannot directly access individual tenant's business data (orders, products, etc.). Access is limited to tenant metadata, configuration, and usage statistics.

### Audit Log Design

1. **Dedicated Audit Table**: Admin actions are recorded in a separate audit log table (`admin_audit_logs`) with fields: admin_user_id, action, target_type, target_id, changes (JSONB), ip_address, user_agent, timestamp.

2. **Service-Level Auditing**: Audit entries are created at the application service layer (`AdminAuditService`), not at the middleware level. This ensures only meaningful business actions are logged, not every HTTP request.

3. **Change Tracking**: For state-changing operations, both old and new values are captured in the `changes` JSONB field, enabling a full diff view.

4. **Immutable Logs**: Audit log entries are append-only. No update or delete operations are exposed. Retention policy can be applied at the database level.

5. **Query Capabilities**: Audit logs can be filtered by action, target type, date range, and admin user. Results support pagination and CSV export.

## Consequences

### Positive
- Tenant isolation remains intact for all regular operations — admin bypasses are explicit and controlled
- Full audit trail for compliance (who did what, when, from where)
- Change diffs enable forensic analysis and rollback decisions
- Separation of admin and tenant APIs prevents accidental cross-contamination
- Append-only audit logs cannot be tampered with by admin users

### Negative
- Admin repository methods must be carefully maintained to avoid scope leaks
- Audit log table will grow continuously — needs retention/archival strategy
- JSONB changes field is flexible but harder to query than normalized columns
- No real-time alerting on suspicious admin actions (could be added later)

### Alternatives Considered
- **Option A: Disable Tenant Filter for Admin Users at ORM Level** — Automatically unscope all queries when request is from super admin. Rejected: too dangerous, a bug in any handler could leak cross-tenant data.
- **Option B: Middleware-Level Audit Logging** — Log every HTTP request/response for admin routes. Rejected: too noisy, captures irrelevant GET requests, doesn't capture business semantics.
- **Option C: Event Sourcing for Admin Actions** — Use domain events as the audit trail. Rejected: adds complexity; domain events serve a different purpose (inter-context communication) and shouldn't be conflated with audit requirements.
- **Option D: External Audit Service (e.g., AWS CloudTrail equivalent)** — Rejected: over-engineered for current scale, adds operational dependency.

## Trade-Offs
- **Pros**: Strong isolation, comprehensive audit, simple implementation
- **Cons**: Manual scope management, growing audit table, JSONB query complexity
- **Risk Level**: 🟡 MEDIUM — Cross-tenant queries bypass a core security boundary; mitigated by dedicated service layer, middleware protection, and code review requirements
